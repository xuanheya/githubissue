## #613 信息不足时怎样回答

[原 Issue](https://github.com/AsyncFuncAI/deepwiki-open/issues/613) 仅报告等待约一小时。保存的运行进行了 5 次仓库调用、4 次模型调用，查询了几个可能发生等待的阶段。报告首先追问「是哪一步花了一小时」，并要求时间线、模型和部署信息。返回的 3 段源码均已按固定提交核对。

这个案例也暴露了当前模型的局限：对只有一句描述的 Issue，它有时仍会用足数次检索。源码可以帮助设计问题，但不能证明该用户的实际瓶颈。报告的假设排序需要用户的时间线验证。[面板截图](evidence/sparse.png) · [运行记录](evidence/sparse.json)

## 重复验证

1. 按 README 启动后端，运行 `npm run demo:live`。脚本加载真实 MV3 扩展，打开 #585，提交背景，检查 Session 和版本、源码链接、旧证据及新背景引用，并保存两版截图。
2. 运行 `npm run demo:live -- --sparse`，在 #613 检查提问是否能区分不同耗时阶段。模型自主选工具，每次调用数、措辞和排序可能不同。
3. 运行 `uv run --locked pytest -q` 验证 CSV 确定性用例。现有证据足够时零次仓库读取即可更新；新背景指向后台导出时重新搜索并打开对应文件。这些用例使用可控工具响应和模型消息，覆盖与真实调用相同的 mini-SWE-agent 循环。
4. 运行 `npm run test:browser` 验证扩展入口、失败重试、刷新恢复、Issue 隔离、安全文本渲染与 PR 排除。此命令自行启动独立端口，不会占用当前服务。
