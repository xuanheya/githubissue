# 验收演示 · DeepWiki-Open 的流式输出问题

**目标**是在一个真实 Issue 上观察 Agent 如何选工具、给出可证伪的判断，以及如何在收到新证据后调整排查顺序。案例来自 [AsyncFuncAI/deepwiki-open #585](https://github.com/AsyncFuncAI/deepwiki-open/issues/585)。

Issue 报告了两条异常。先出现的是流式客户端读取事件的 `choices` 属性时失败，随后 Wiki 结构解析出现 XML 错误。报告者给出了依赖版本、调用栈和自己的归因。演示中的补充背景是人为设定的另一条观察，未发布到 GitHub。

## 已完成的真实验收

2026 年 11 月 23 日使用 DeepSeek 官方 `deepseek-flash`、真实 GitHub API 和 Chrome for Testing 145 加载本项目扩展。两次成功结果的 sessionId 相同，revision 从 1 变为 2。完整建议、工具返回与证据编号可在[两轮原始记录](evidence/run.json)中核对。

| | 第 1 版 | 补充背景后的第 2 版 |
|---|---|---|
| 优先排查 | 记录最初流事件的类型，核对何时读取了 `choices`、是否已输出文本 | 用请求 ID 和时间对齐两份日志，比较文本长度、终止原因及异常，区分流解包失败和输出截断 |
| 实际取证 | 一次 Issue 读取，2 次路径搜索，2 次片段读取；初次提交漏了步骤的证据字段，校验器拒绝后模型自行修正 | 2 次路径搜索，2 次片段读取，其中 1 次关键词未命中；新增 R3 并沿用 I1、R1、R2，更新依据包含 C1 |
| 实现依据 | R2 显示流异常进入研究服务的异常处理，[查看固定提交](https://github.com/AsyncFuncAI/deepwiki-open/blob/f216676fa37042c04eba3ccef56098d011670913/api/services/research.py#L252-L311) | R3 显示 OpenAI 兼容流处理代码直接读取 `chunk.choices`，[查看固定提交](https://github.com/AsyncFuncAI/deepwiki-open/blob/f216676fa37042c04eba3ccef56098d011670913/api/chat/_stream.py#L168-L247) |
| 面板 | [查看第 1 版截图](evidence/revision-1.png) | [查看第 2 版截图](evidence/revision-2.png) |

**人工核对发现一处措辞错误。** 第 1 版首步把“模型事件缺少 choices”对应的“缺失计数”写成了 0。若按缺失次数计数，正确的判断应是 **大于 0**；也可以直接观察首个事件是否具有该属性。原始截图和 JSON 保留了实际回答。运行中的字段、编号校验能拦截缺字段的结果；验证标准的语义仍需维护者核对。

## 在 Chrome 中演示

1. 按 README 配置本地后端并加载扩展。打开 #585，点击右下角「生成处理建议」。
2. 核对第 1 版标题及链接。读第一条处理步骤，找出它要求观察的具体信号。展开「假设、证据与本轮工具记录」，点击 R 编号对应的来源，核对引用的是默认分支某个提交中的具体行。
3. 在同一面板输入下面这句话，点击「更新建议」。

   > 我这次失败的请求已持续输出了非空文本，最后一条模型事件注明达到输出长度上限，传给解析器的文本缺少 `</wiki_structure>`。

4. 核对面板变为第 2 版，且「本次更新」引用了 C1。对比第一步、待澄清项和假设。新样本有输出，原报告称没有输出；合理的新版会区分这两种路径，并给出验证截断和核对请求归属的方法。
5. 刷新页面应恢复第 2 版。切换到另一 Issue 应看到该页自己的入口。所有操作都在本地扩展和后端完成。

## 自动运行同一演示

在第一终端运行 `npm start`。在项目根目录的另一终端执行以下命令，需能访问 GitHub 和真实模型端点。

```sh
npx playwright-core install chromium
npm run demo:live
```

脚本启动临时 Chrome for Testing 配置，加载交付的 MV3 扩展，打开真实 Issue，并通过页内按钮完成两轮。它会校验原始链接、相同 Session、版本递增和 C1 引用，输出 `demo-output/revision-1.png`、`revision-2.png` 和 `run.json`。JSON 保存两轮返回的证据、工具轨迹和建议。模型选择的文件与具体措辞可能随运行变化。

## 面试时的追问

- **怎么判断它会不会自主搜索？** 展开某一版的工具记录，核对实际目的、命中项和读取片段。信息充分时也允许直接提交；单元测试覆盖零检索分支。
- **怎么证明它结合了新增信息？** 对照两版步骤，指出 C1 改变了哪一个排查分支、还缺什么观察。JSON 中的 sessionId 和 revision 用来验证会话连续性。
- **为什么正文里的命令不会直接执行？** 工具名单只提供路径查询、文本读取和结果提交。仓库、URL、文件编号和预算由后端约束。自动化测试会尝试调用名单外的工具，并检查拒绝记录。
